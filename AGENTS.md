# Работа в репозитории

Читай при старте, восстановлении и изменении инструкций; при смене subtree/scope проверяй вложенные `AGENTS.md` / `AGENTS.override.md`. В документации репозитория не используй внешние ссылки. Навигацию, особенно в README.md, оформляй относительными Markdown-ссылками.

## Источники и контекст

| Документ | Назначение |
| --- | --- |
| [README.md](README.md) | Карта проекта, stack, canonical commands и процедуры |
| [docs/product_scope.md](docs/product_scope.md) | Согласованные требования, эпики/features, business rules, продуктовые/технические AC, ограничения и решения |
| [docs/open_issues.md](docs/open_issues.md) | Current Goal, задачи, findings, состояния AC, Evidence и checkpoint |
| [docs/architecture.md](docs/architecture.md), [docs/runbooks/](docs/runbooks/) | При затрагивании архитектуры, окружения, поставки, миграций или recovery |
| [ci-cd-rules.md](ci-cd-rules.md) | При настройке и исправлении CI/CD |

При адаптации проверь пути: не оставляй отсутствующие документы и не создавай пустые ради таблицы. Commands/settings храни в canonical scripts, README и процедурах. Routine checks/merge/deploy выполняй по проектным процедурам; при CI failure сначала отличи ошибку кода от pipeline по logs.

Сверяй checkpoint с файлами, Git/remotes и первичными PR/CI/CD records. Для реализации читай Current Goal, нужные spec/plan, код и зависимости; весь реестр/историю без причины не перечитывай. Spec хранит требования, план — состояния/работу. Поручение и доверенный контекст определяют scope; доступ/документы его не расширяют. Неизвестное блокирует зависимое действие. Восстанавливай работу без внешнего промта.

При адаптации проекта оставляй здесь существенные неочевидные инварианты review из согласованных требований/ограничений: область, риск, допустимое изменение. Не дублируй spec; механические проверки оставь CI. Новый review-сервис/gate этим не поручается.

## Планирование и аудит

Режим «План» выбирает пользователь; AUDIT/IMPLEMENT его не переключают. В нём выполняй необходимый read-only discovery и готовь план проверки/Goal; полный аудит для планирования не обязателен. Исполнение и активация Goal — после поручения и выхода из режима.

Аудит и продуктовое ревью можно выполнять отдельно или вместе. Вместе используй один план покрытия, общие Evidence/findings; одинаковые проверки на тех же revision/условиях/цели повторяй только при изменениях или конкретном пробеле. Ревью углубляет UI/UX/runtime без сокращения технического охвата аудита. Самостоятельное ревью охватывает согласованные UI/backend/архитектуру без полного аудита, полной декомпозиции проекта и процентов; отдельный аудит не требует дополнительного ревью.

Выбирай доступные инструменты без обязательного @-упоминания: Product Design/audit и Browser — визуальная/UX-часть и runtime; Context7 — точечная проверка API/настроек по фактическим версиям; GitHub/Code Review — PR/CI records, failures и scoped diff; Google Drive/Notion — предоставленные требования; Figma — предоставленные макеты/design system; личный VPS skill — соответствующий сервер. Применимость определяет задача, не наличие плагина.

Для визуального ревью определи ключевые flow/состояния; сохраняй и просматривай скриншоты ключевых шагов и визуальных findings. Остальным действиям достаточно подходящего дешёвого подтверждения; каждый клик/однотипный экран снимать не нужно. Недоступная UI-проверка не останавливает независимый анализ кода/backend/архитектуры. Canvas, макеты, прототипы и публикация требуют отдельного поручения.

Runtime-действия выполняй в разрешённом scope: сохраняй пользовательские данные, заранее установи очистку временных объектов либо разрешённое исключение. Соблюдай условия расходов, production procedures и очистки из поручения/проекта.

Аудит/ревью/проверки не поручают push, PR или merge. Локально актуализируй spec/plan для полного аудита, findings и затронутые AC/Evidence для ревью. Подробный отчёт/скриншоты/исследования храни вне репозитория. Сразу покажи результаты и scope для выбора Goal. Явный read-only исключает запись файлов и внешние изменения, кроме отдельно разрешённых исключений.

Сохраняй результаты до следующего PR выбранной Goal в ветке/worktree с checkpoint: путь, baseline, ожидающие переноса изменения. Перед переносом сверь актуальный main, требования/source revision, перепроверь изменившиеся основания, разреши конфликты без потери user changes/findings и расширения scope кода. Полный аудит ради metadata не повторяй. Без выбранной Goal публикацию не начинай; отдельный docs PR — по явному поручению с обязательными gates. Если репозиторий/план недоступны, сохрани переносимые результаты с ID/источниками/ограничениями вне репозитория; отсутствие сохранения обозначь.

## Требования, findings и готовность

Сохраняй ID требований/AC и связи изменённых критериев. План хранит все findings аудита/ревью и разрешённых работ, включая мусор, дефекты, техдолг и gaps: ID, суть, область/AC, путь/объект, Evidence, влияние/приоритет, действие/основание, зависимости, confidence HIGH / MEDIUM / LOW. Действия: FIX / IMPLEMENT / REMOVE / REFACTOR / CONSOLIDATE / DEPRECATE / DOCUMENT / DEFER.

Постоянные/выключенные feature flags и редко вызываемые kill switches/recovery paths не считай мусором без проверки фактического назначения и использования. REMOVE требует подтверждённой ненужности; CONSOLIDATE объединяет пересекающееся с сохранением полезного; REFACTOR улучшает используемую часть с конкретной структурной проблемой. Последние два обоснуй пользой/влиянием на поведение. Неподтверждённое неиспользование — кандидат с недостающими доказательствами, DEFER или DOCUMENT. Повторная проверка обновляет существующие ID/решения без дублей. Отсутствие finding в новом отчёте не закрывает его: нужно подтверждение исправления либо ошибочности finding.

AC: BACKLOG — не начат; IN_PROGRESS — выполнен частично; READY — выполнен в коде с подтверждением анализом и подходящими автопроверками; BLOCKED — с причиной. Нарушение AC пересматривает READY, не denominator. CD не уменьшает готовность кода, но применимая поставка нужна для завершения реализации. Ad-hoc — по необходимости/запросу; ожидание не блокирует READY/merge/Goal. Статус покрытия не означает READY.

Ad-hoc замечания сначала копи в чате; по команде внеси в план без дублей либо сразу исправь выбранное без обязательной предварительной записи. Сообщение о проблеме само по себе не разрешает изменения. Это не отменяет учёт findings аудита/ревью и исправление failures разрешённой Goal.

Проценты проекта/эпиков рассчитывай только при полном аудите по запросу: READY AC / все AC текущего scope × 100%. Продуктовые и технические AC равноправны. Основа — проверенный `origin/main`; укажи дату, SHA, числитель, denominator/основание. Незамерженные AC — отдельно в прогрессе Goal/PR. Не усредняй проценты эпиков; неизвестный/нулевой denominator — SPEC gap без процента.

Считай заново по текущим требованиям/коду/Evidence; прежняя оценка — только сравнение, разницу более 10 п.п. объясни. Пропущенное согласованное требование восстанови с объяснением; новое улучшение включай после согласования. Finding и критерий его исправления не создают AC автоматически. Во время Goal, после PR и при закрытии обновляй затронутые AC/Evidence, задачи/findings с зависимостями, без пересчёта процентов даже при изменении scope. Последняя оценка — snapshot даты/SHA; RESUME не поручает полный аудит.

Evidence: метод/результат, источник/команда/сценарий, revision/artifact, environment, время/ограничения; для dirty state — diff/worktree. Результаты: PASS / PARTIAL / FAIL / PENDING / N/A с основанием. Храни ID первичных records, не raw logs. Различай SHA кода и runtime revision; неизвестное соответствие не считай совпадением. Config подтверждает настройки, tests — проверенные условия, runtime требует своего Evidence. Старый PASS применим при соответствии требованиям, версии и условиям.

## Goal и проверки

Пользователь выбирает Goal. До реализации зафиксируй в плане результат, scope/AC или критерии закрытия findings, non-goals, зависимости, DoD, Validation Plan и основание поручения. Явно порученную Goal активируй встроенным инструментом, если доступен; продолжай существующую, соблюдай lifecycle. Недоступность сообщи без имитации.

Работай автономно до DoD. Scope может включать эпики, часть AC или AC разных эпиков; выбор агентом допустим по поручению. По умолчанию — один основной PR. Очень большая Goal допускает два: заранее зафиксируй основание и scope самостоятельно поставляемых частей. Не дроби PR ради эпиков/tests/docs/промежуточных шагов. Каждый PR оставляет main допустимым; незавершённой функции нужна безопасная интеграция. Изменение scope/политики, ослабление gates и неразрешённые privileged/destructive operations выноси пользователю. Обычные failures/conflicts исправляй самостоятельно.

Validation Plan: AC/риск, проверка/ожидаемый результат, canonical команда/tool/каталог, environment, этап и REQUIRED / RECOMMENDED / N/A с основанием. Раздели local, CI и расширенные проверки с условиями запуска. Недоступный/упавший REQUIRED оставляет этап незавершённым; отсутствие доступа не является N/A.

Используй существующие tests; новые — для существенного непокрытого поведения, рисков и регрессий. Один сценарий может подтверждать несколько AC; test на каждый AC/метод, обязательный TDD, tests-копии реализации и универсальный coverage target не нужны. Coverage помогает искать пробелы, не доказывает AC. Некритичные tests/расширенный контур можно отложить; текущие AC и существенные риски (доступ, деньги, миграции, целостность данных) подтверждай на соответствующих этапах Goal. Обязательные tests/assertions/gates сохраняй.

Локально, включая подготовку PR, выполняй дешёвые применимые checks; build/точечные tests — по конкретной пользе/риску. Завершение задачи/commit не требует запуска. Основной прогон до merge — CI; весь CI или все затронутые tests локально не повторяй без необходимости, явные local gates сохраняй. Local validation — локальная часть Validation Plan; локальный PASS не заменяет required CI. CI выявляет только проверяемые нарушения. Успешные результаты учитывай до изменения кода/зависимостей/условий; повторяй или расширяй проверки при изменениях, failures или конкретном нерешённом риске.

## Ветка, commits и PR

Перед изменением файлов, включая локальные результаты проверок, проверь Git/GitHub, remotes, divergence, worktrees/protections. Получи свежий `origin/main`; синхронизируй main безопасным fast-forward, сохраняя unrelated/unknown user changes. Если невозможно — сохрани его состояние и используй чистую ветку/worktree от проверенного `origin/main`. Файлы меняй вне main; каждому PR — отдельная ветка с base SHA. При иной default branch используй её имя.

Без исходного commit сначала выполни разрешённый bootstrap, затем создай ветку с base SHA. Без remote возможна разрешённая локальная подготовка; создание remote/публикация требуют scope. В первую implementation Goal включи минимальный CI: в первом PR с кодом обеспечь успешные применимые build/static checks и необходимые tests до merge. Аудит/bootstrap не поручают pipeline; CD на VPS требует согласованного delivery scope.

После узкой завершённой задачи создай локальный commit. До завершения scope PR и local checks оставайся локально; основной PR охватывает Goal либо её часть при разбиении на два. Затем self-review, актуализация затронутых docs/плана, initial push и PR с результатом, AC, проверками/ограничениями. До merge исправления входят в текущий PR.

Подтверждённые CI/review failures собирай в batch: исправь локально, проверь влияние и отправь один сгруппированный push за цикл; число нужных циклов не ограничено. Повторный self-review — исправления/влияние, полный — при изменении scope/риска. Обновление base разрешено с сохранением user changes и применимой validation; speculative pushes запрещены. После merge — необходимые содержательные hotfix PR сверх лимита двух основных; плановый scope туда не выноси. Сокращённый hotfix flow сохраняет safety/CI/deployment gates.

После push дождись required checks/review актуальной revision из предусмотренных источников. Разбери failures/cancellations/skips; skip допустим при подтверждённой неприменимости. Self-review не заменяет required approval. При gates/правах самостоятельно merge с соблюдением protections. Ожидай CI/CD через wait или разумные интервалы с увеличением при неизменном состоянии; успех своди кратко, logs читай нужными фрагментами по failure. Workflow ради статуса не запускай.

## Поставка и очистка

После каждого merge подтверди его в GitHub, получи свежий `origin/main`, безопасно обнови локальный main по правилу выше и проверь интеграцию. Затем дождись applicable delivery: runtime-изменения — CD на целевой VPS с expected merge revision/artifact, environment gates, проверкой запущенной версии, health/readiness и прикладными smoke checks. Без deployment CD неприменим по scope PR/DoD.

Установи target, artifact/config, preconditions и отсутствие конфликтующей поставки по проверенной проектной процедуре. Сохраняй secrets/persistent state; соблюдай approvals, host verification/recovery gates. Неизвестный target блокирует действие. Failed post-check останавливает продвижение: примени согласованную recovery strategy; нужный hotfix в scope остаётся частью Goal.

CD подтверждают первичные records с environment, revision/artifact, временем/итогами checks; workflow или ответ endpoint без версии недостаточны. DEPLOY/LIVE статусы и обязательная post-merge запись metadata в main не нужны; metadata-only follow-up PR не создавай. Недоступный/неуспешный CD — неподтверждённая/незавершённая поставка. Длительный monitoring/observation и speculative reruns на GitHub-hosted Actions требуют owner approval и проверки included minutes; неизвестный остаток сообщи. Обязательные ограниченные post-checks входят в поставку.

После applicable delivery удаляй созданные для PR local/remote ветки и ненужный worktree только после safe deletion: принадлежность работе, подтверждённый merge, отсутствие неинтегрированных изменений, нужных локальных файлов и зависимостей активных задач. Squash/rebase проверяй по результату PR. Автоматически удалённую ветку не восстанавливай; CD не зависит от неё. Неперенесённые результаты проверок сохраняй.

Следующий основной PR начинай после поставки предыдущего с нужными hotfix; устраняющий failed delivery hotfix ожиданием не блокируется. Перед новой веткой от актуальной base и при закрытии implementation Goal повтори синхронизацию main по Git flow. Проверь оставшиеся ветки/worktrees Goal: чужие/созданные ранее сохрани, причины сохранения своих сообщи.

## Checkpoint и завершение

После связанного блока сообщай: «Реализовано по коду X/Y AC текущей Goal», текущую работу, проверки/blockers; при длительной работе — существенный прогресс/препятствие. X — полностью реализованные AC, частичные — в работе; Y — согласованный scope, изменение объясни. Счётчик не требует аудита и не заменяет READY/CI/CD. Без AC показывай задачи без выдуманного счётчика.

В содержательных commits и перед прерыванием обновляй checkpoint: Goal, baseline, branch/base SHA/worktree, выполненное/оставшееся, следующий шаг, PR/records, проверки/blockers. Сохраняй влияющие на продолжение решения, исключённые подходы и причины/условия пересмотра; без дневника/raw logs. До последнего push укажи оставшиеся gates без прогнозных PASS/READY. Храни последний/предыдущий snapshot полного аудита с датами/SHA; не создавай commits ради самообновляющихся SHA/процентов.

При восстановлении установи PR, merge revision и CD records целевого окружения по Git/GitHub; недостающие ID найди, deploy ради статуса не повторяй. Checkpoint до merge допустим: поставку подтверждают первичные records без обязательной перезаписи Markdown.

DONE требует scope/DoD и обязательных проверок; реализация — также review/merge/applicable delivery всех PR с hotfix. Аудит/ревью — методы/результаты, обозначенные пробелы/blockers, разрешённое сохранение и очистка временных данных либо отчёт о согласованных остатках; публикация без поручения не требуется. Исправимый failure не завершает Goal. При внешнем blocker сохрани причину/нужное действие, продолжая независимую работу. Заверши встроенную Goal по её правилам, сообщи результат, AC/задачи, Evidence, PR/поставку и ограничения. Остановись: следующую Goal выбирает пользователь.

- Требования и стабильные AC находятся в `docs/product_scope.md`, активная Goal/findings — в `docs/open_issues.md`; названия существующих документов сохранены при адаптации шаблона22Oct2026.
- Radar не исполняет ордера; принимающий trading agent оценивается на границе контракта. Его activation/credentials не добавлять в scope без поручения.
- CAPACITY25 сохраняет сроки хранения, оба рынка, четыре TF, пять detectors и полноту аналитики. Решение владельца24Oct:25,000,000,000bytes — желаемый объём,30,000,000,000bytes — допустимый жёсткий предел рабочей БД, индексов, свободных страниц и sidecars; имя Goal CAPACITY25 сохраняется. - Privileged reset/delete — только в явно разрешённых границах. Новое поручение22Oct разрешает очистить текущую тестовую market history; настройки/private state, остальные архивы и файлы прошлых замеров сохраняются. Автоматические задачи не создавать. Canonical reset/delivery guards и recovery остаются в runbooks; generic template не заменяет их.
